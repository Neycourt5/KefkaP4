7. FLOOD OF NAUGHTS — ROOT CAUSE
--------------------------------------------------------------------

Reported symptom: plugin said REAL; player held the purple debuff and a
blue-person icon; player stood in purple ("same colour"); result looked wrong.

Mapping the reported colours to debuffs:
  purple            = Black Wound      (ShapeRenderer black = 0.48,0.35,0.72)
  blue person icon  = Allagan Field    (StatusHud AllaganField = 0.20,0.43,0.85)
  (Beyond Death renders red, White Wound near-white — neither was described.)

So the case was: Black Wound + Allagan Field + REAL Flood.

Per p4_seq.gd, black wound is black-safe when (i >= 4) != flood_fake. Allagan
Field means i < 4, and REAL means flood_fake == false, so:
  (false) != (false)  ->  false  ->  WHITE-safe.

The required answer was the WHITE Antilight. The player stood in purple/black.
That is a genuine fail, and the plugin graded it correctly.

ROOT CAUSE: not a code defect. The player's rule-of-thumb ("be hit by the same
colour") is only correct for Beyond Death holders on a real Flood. The actual
rule combines three inputs:

  Allagan Field -> OPPOSITE colour
  Beyond Death  -> SAME colour
  Fake Flood    -> inverts both

The trainer never surfaced that conclusion. The pre-existing cue said only
"Flood: Real / Black West", which names the compass side of black but not which
side the PLAYER should take. All the inputs were on screen as icons; the
derivation was left to the player under a 5.3s cast.

Verified as correct against Waju, and left unchanged:
  - assignment sets            (KefkaP4Assignments.Generate)
  - expectedWest selection     (ResolveFlood)
  - strict > 0 / < 0 boundary  (matches Waju exactly; centre line fails neither)
  - bot destinations           (MoveFlood)
  - west/east rectangle colour (AddFloodHalf; west is Black iff black_west)

One subtlety that had to be settled to read the source at all: GDScript
comparison operators are left-associative and do NOT chain like Python's, so
`i >= 4 != flood_fake` is `(i >= 4) != flood_fake`. The chaining reading makes
flood_fake inert for white wounds, contradicting the author's own comment. The
existing C# already used the left-associative reading.

FIX MADE: added FloodBriefing (KefkaP4Flood.cs), built from the same assignment
sets the grader reads, exposing the resolved side, the resolved Antilight
colour, whether that matches the wound colour, and a plain-language
explanation. Wired into:
  - CurrentCue          -> "Flood Real: go WEST into White Antilight"
  - ResolveFlood reason -> "wrong Antilight side: needed White (WEST)"
  - DebugWindow         -> new "Flood of Naughts" section

TESTS ADDED (KefkaP4Trainer.Core.Tests/FloodOfNaughtsTests.cs):

C. DALAMUD API 15 OBSERVATION SURVEY (the gate on the healer feature)
--------------------------------------------------------------------

Surveyed Dalamud.xml and FFXIVClientStructs.xml in the 15.0.3 dev distribution.

FINDING: there is NO action or combat-event service in API 15. The full
IDalamudService list contains nothing equivalent to an "action used" callback.
Everything must be polled from state the game already publishes.

Usable, in order of reliability:
  1. IBattleChara.IsCasting + CastActionId + CurrentCastTime/TotalCastTime
     -> casted actions only. High confidence, gives CastTargetObjectId.
  2. ActionManager.IsActionOffCooldown + GetCurrentCharges
     -> instants and oGCDs. The ONLY safe way to see them.
     NOTE: GetRecastTimeElapsed does NOT exist in this ClientStructs version.
     Available recast members are exactly: GetRecastTime, GetRecastTimeForGroup,
     GetAdjustedRecastTime, GetAdditionalRecastGroup, GetCurrentCharges,
     IsActionOffCooldown, StartCooldown. GetRecastGroupDetail is absent.
  3. IBattleChara.StatusList -> status appearance. NOT implemented yet.

HARD LIMIT: an instant *GCD* cannot be identified. Every GCD shares one recast
group, so the group tells you a GCD fired but not which one. Documented in
ObservationCapabilities.Notes and shown in the healer window rather than
papered over.

Also discovered: IDataManager was not registered in Services.cs. Added, so the
action database can be cross-checked against the Lumina Action sheet.

D. WHAT THE TESTS CAUGHT
--------------------------------------------------------------------

Writing VirtualPartyTests/DamageTableTests corrected three things:

  1. White Antilight is NOT a wrong-side one-shot. At party-total scope it is
     92,625 against a 148,000 pool. The source log is a clear, so the figure is
     what the party took on its CORRECT side. LethalByDesign removed; the
     wrong-side outcome stays a Flood mechanic failure, not a damage number.
  2. Effect windows are half-open everywhere in this codebase, so a 9s regen on
     a 3s interval ticks at 3 and 6 but not at 9. Test expectation corrected and
     the convention documented.
  3. REAL BUG: SimulatedMember.TakeDamage reported HpLost as the incoming
     damage, so a 300k hit on a 100k pool logged "hp -300,000". Now clamped to
     HP actually removed, with the excess reported as a separate Overkill field.

Reference-scope reasoning is asserted, not assumed:
UnmitigatedRaidwidesAreSurvivableAtTheReferencePool fails if the figures are
ever read as per-target, because every Grand Cross would then be a double
overkill. The same test also asserts the full unmitigated sequence still wipes,
so the numbers cannot drift soft either.

B. VIRTUAL CO-HEALER
--------------------------------------------------------------------

Classification: WHM/AST -> virtual BARRIER co-healer; SCH/SGE -> virtual PURE
co-healer. Non-healer jobs get none.

Profile behaviour:
  barrier  Sacred Soil (mit) + Succor (shield) pre-cast, Kerachole regen,
           Lustrate emergency
  pure     Plenary Indulgence (mit) pre-cast, Cure III post-damage heal,
           Medica III regen, Benediction emergency

Everything is emitted as ObservedHealerAction through the SAME
HealerActionApplier a real observed press uses. HP is never touched directly
and boss damage is never reduced; all contribution appears in the action log
and party history attributed to "co-healer (barrier|pure)".

TWO FINDINGS FROM THE TESTS:

  1. Presets escalate by CATEGORY, not magnitude. Scaling one healer's numbers
     up and down would teach the player to expect heal sizes that no real
     co-healer produces.

  2. REAL DESIGN DEFECT, caught only by running the full phase: Standard
     originally answered EVERY raidwide with mitigation + shield + heal and
     carried the pull outright. That is a duo's output, not one healer's.
     Fixed with CoverageStride: Standard takes alternate raidwides and the ones
     in between are the player's, which is how a real pair splits cooldowns.
     Strong keeps stride 1 and can carry the phase - that is its purpose.

CALIBRATION NOTE: the scripted phase totals ~336k per player against a 148k
reference pool, so NO lone healer completes it. Assistance levels are therefore
validated on time-to-first-death, not survivor count.

Determinism: no randomness; fired-key set against replay; half-open
(previousTime, time] window so a scrub backwards emits nothing; Reset() clears.

Tests: 19 in VirtualCoHealerTests covering classification, all five levels,
both profiles, determinism, replay, scrub, reset, emergency threshold and
cooldown, dead-target skipping, attribution, and dedup keyspace isolation.

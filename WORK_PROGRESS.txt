7. FLOOD OF NAUGHTS — ROOT CAUSE
--------------------------------------------------------------------

Reported symptom: plugin said REAL; player held the purple debuff and a
blue-person icon; player stood in purple ("same colour"); result looked wrong.

Mapping the reported colours to debuffs:
  purple            = Black Wound      (ShapeRenderer black = 0.48,0.35,0.72)
  blue person icon  = Allagan Field    (StatusHud AllaganField = 0.20,0.43,0.85)
  (Beyond Death renders red, White Wound near-white — neither was described.)

So the case was: Black Wound + Allagan Field + REAL Flood.

Per p4_seq.gd, black wound is black-safe when (i >= 4) != flood_fake. Allagan
Field means i < 4, and REAL means flood_fake == false, so:
  (false) != (false)  ->  false  ->  WHITE-safe.

The required answer was the WHITE Antilight. The player stood in purple/black.
That is a genuine fail, and the plugin graded it correctly.

ROOT CAUSE: not a code defect. The player's rule-of-thumb ("be hit by the same
colour") is only correct for Beyond Death holders on a real Flood. The actual
rule combines three inputs:

  Allagan Field -> OPPOSITE colour
  Beyond Death  -> SAME colour
  Fake Flood    -> inverts both

The trainer never surfaced that conclusion. The pre-existing cue said only
"Flood: Real / Black West", which names the compass side of black but not which
side the PLAYER should take. All the inputs were on screen as icons; the
derivation was left to the player under a 5.3s cast.

Verified as correct against Waju, and left unchanged:
  - assignment sets            (KefkaP4Assignments.Generate)
  - expectedWest selection     (ResolveFlood)
  - strict > 0 / < 0 boundary  (matches Waju exactly; centre line fails neither)
  - bot destinations           (MoveFlood)
  - west/east rectangle colour (AddFloodHalf; west is Black iff black_west)

One subtlety that had to be settled to read the source at all: GDScript
comparison operators are left-associative and do NOT chain like Python's, so
`i >= 4 != flood_fake` is `(i >= 4) != flood_fake`. The chaining reading makes
flood_fake inert for white wounds, contradicting the author's own comment. The
existing C# already used the left-associative reading.

FIX MADE: added FloodBriefing (KefkaP4Flood.cs), built from the same assignment
sets the grader reads, exposing the resolved side, the resolved Antilight
colour, whether that matches the wound colour, and a plain-language
explanation. Wired into:
  - CurrentCue          -> "Flood Real: go WEST into White Antilight"
  - ResolveFlood reason -> "wrong Antilight side: needed White (WEST)"
  - DebugWindow         -> new "Flood of Naughts" section

TESTS ADDED (KefkaP4Trainer.Core.Tests/FloodOfNaughtsTests.cs):
  - BlackSafeMembershipMeansStandingInTheBlackAntilight  (400 seeds x 8 roles)
  - SafeSetsPartitionTheParty
  - AssignmentMatchesWajuTruthTable                      (8-row [Theory])

9. ICE / LIGHTNING PLACEMENT
--------------------------------------------------------------------

Both badges now project from their own world anchor above the arena centre:

  MagicTellLightningHeight  default 4.2 yalms  (shoulders/head)
  MagicTellIceHeight        default 1.2 yalms  (knees/lower legs)
  MagicTellHorizontalSpread default 0, simulator units, applied in opposite
                            directions on the arena X axis

All three are sliders under Settings, and each badge is skipped independently
if its own anchor fails to project. The caption rides above whichever badge is
higher on screen rather than assuming lightning always is.

CAVEAT: the two default heights were chosen from arena scale (47 simulator
units = ~20.4 yalms radius), NOT from measuring Kefka's model. They are the
most likely thing to need tuning during in-game verification.
